# 05 复盘

## 1. 最难的三件事

**真实模型不可控，但证据必须可复现。** 验收要求至少两条执行路径的运行记录，我最初的想法是让模型跑出"超时长 → 压缩"，可真实模型不一定首稿就超时，赌它发挥等于把验收交给运气。后来正式证据换成"刺激必然发生"的场景：注入工具超时（AC-04a）、空素材检索必然 0 结果（AC-08b no_hit），模型必须对这些结果做反应；38→28 只作离线确定性参考证据，并明确标注 mock 边界。这个决定比多跑几次模型有用。

**"完成"到底谁说了算。** 模型会自己调 `finish` 说完成了，也有模型声明"无法满足"但其实能通过的时候。最后把判定权收到 finalize 节点：对最新提交稿用纯函数重新估算、重新检查，模型的话只当意图。这是整个项目里最有效的一条设计——把"模型自评"变成了可复算的事实。

**trace 里的决策依据从哪来。** 真实模型带 tool_calls 时 content 经常是空的，一开始想用模型自己写的话当依据，实测发现靠不住。最后拆成两列：`decision_note` 是模型可见输出，缺了如实标 `missing`；`decision_summary` 是编排层按实际观察和实际调用拼的事实摘要，标 `source=orchestrator`。宁可把来源写清楚，也不假装是模型说的。

## 2. 返工记录

- 第一版设计把真实模式判定写死成 ≤30 秒，和 ±10% 容差冲突，被我打回重改。
- 第一版证据计划默认"真实模型会超时"，改成必然触发场景，避免赌模型行为。
- `ToolCall.raw_arguments` 那处提交不自洽，单测和本地运行都看不出来，干净 checkout 才发现。
- 两个真机问题（`NO_PROXY` 让 httpx 构造崩溃、tools 格式导致 HTTP 422）都是单测注入 transport 覆盖不到、只有真跑才暴露的。
- 复跑命令文件多写了一个 `run`，19 个里 18 个不能执行，最后靠逐条解析才抓全；测试里加一条"命令文件能被 argparse 解析"的用例就能防住。

## 3. 学到什么

- 单测注入 transport 会把真实网络层的问题全部藏起来，至少要留一条真机冒烟。
- 每个提交要能独立跑绿，否则历史是假的；干净 checkout 复验值得定期做。
- mock 的边界要在文档里写死，不然读者会把流程证据当成模型能力证据。
- 证据宁可少而真：真实模型的数字不一样就写不一样，不补写、不拼接、不把不同分支写成同一件事。

## 4. 还没做的

- AC-08a 的真实模型对照没跑，只有离线确定性对照，属于加分项，不影响硬约束验收。
- 真实模型只跑了 6 组证据，没有做多轮稳定性抽测；同一输入可能得到不同文本。
- 素材、品牌/平台规则、时长公式都是合成或近似值；换成真实语速和平台规范需要重新标定。
- 语义级事实误用（有引用但张冠李戴）目前靠人工评审，后续可以加一次复核：拿引用原文和旁白逐句对照，让模型判"是否等价"。
- 如果继续做，下一步是把"脚本可编辑"做深：直接导出口播稿、分镜表给剪辑用，以及把规则检查拆成可配置的规则包。

## 5. 对 AI 协作的判断

这次 AI 写得快、改得也快，但出错的地方很集中：一是环境相关的真实调用（httpx、proxy、API 格式），二是"证据的诚实性"（命令文件、提交自洽、数字口径）。所以我的用法是：让 AI 负责产出，我负责所有能证伪的环节——自己跑、自己核对、自己决定哪些数能写进论文档。复核成本不低，但比返工便宜。
